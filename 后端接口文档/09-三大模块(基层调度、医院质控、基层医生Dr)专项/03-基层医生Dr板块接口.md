## 2. 5.1 视频展示（前端契约，非 REST）

### 2.1 能力说明

| 项 | 内容 |
|----|------|
| 页面 | `/#/dr`，class `dr-page` |
| 增强脚本 | `public/assets/dr-video-enhance.js` |
| 行为 | 将播放列表中带 `data-topic` 的条目替换为 Bilibili `<iframe>`，隐藏原 `<video src="/media/...">` |
| 样式 | `theme-light.css`：`.dr-player--bili`、`.dr-player-panel--bili` |

### 2.2 内置 topic → BV 号映射（可扩展）

| data-topic | Bilibili BV | 说明 |
|------------|-------------|------|
| cpr | BV1Sp4y1z7wN | CPR 相关 |
| earthquake | BV1sA411J7WY | 地震创伤 |
| flu | BV1BmCLBmE3D | 流感/呼吸道 |

未配置 topic 的条目仍指向 `/media/*.mp4`（仓库内文件可能缺失，需自备或继续走 Bilibili 映射）。

### 2.3 生产接入建议（接口化可选）

若需运营可配视频，可增加配置接口（**规划，未实现**）：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/dr/playlists` | 返回 `{ items: [{ id, title, topic, provider, embedUrl, coverUrl }] }` |
| PUT | `/api/v1/dr/playlists/{id}` | 管理端维护 |

当前**不强制**后端；静态 JS 映射即可满足演示与内网联调。

#### 代码逻辑（规划落地参考）

依据：05 `dr_video` 表（模块 5 §5.1；现状前端硬编码 `BILI_VIDEOS` 映射，入库后配置化，05 §6-7）。

1. **查询**：`dr_video` WHERE `enabled = 1` ORDER BY `sort_order`（05 排序列）。
2. **items[] 映射**：`id / title / topic`（`topic` → data-topic，前端 iframe 映射键）；`provider` ← `source_type`（05 枚举 `LOCAL / BILIBILI`）；`embedUrl` = `BILIBILI` → `https://player.bilibili.com/player.html?bvid={bvid}`、`LOCAL` → `local_path`；`coverUrl` 预留 null（05 无封面列）。
3. **返回** `{ items: [...] }`（本节规划契约）。
4. **管理端 PUT**：校验 `title / topic / source_type / bvid / local_path / sort_order / enabled`——应用层校验 `source_type = BILIBILI → bvid` 必填、`LOCAL → local_path` 必填（05 注释）；UPDATE `dr_video`（按 `id`），返回新值。

## 4. 接口清单 · 医生管理

### 4.1 GET `/api/v1/doctors` — 基层医生列表

**Query**

| 参数 | 说明 |
|------|------|
| org_id | 按机构 |
| user_status | USER_ACTIVE / USER_DISABLED |
| keyword | 姓名 / 账号 / 手机模糊 |
| page / per_page | 默认 15 |

**DoctorResource**

| 字段 | 说明 |
|------|------|
| id | users.id |
| real_name / username | 姓名 / 账号 |
| org_id | 机构 ID |
| org | OrganizationResource（whenLoaded） |
| phone / email | |
| identity_type | DOCTOR |
| home_route | |
| user_status | |
| last_login_at / created_at / updated_at | ISO 8601 |

**注意**：响应不含 `password_hash`。

#### 代码逻辑

依据：04 §5.3.3（Dr 页 `list('/doctors', { per_page: 20 })` 并行面板请求）+ 05 `sys_user` 表（P.2）。

1. **参数校验**（本节 Query 表）：`org_id`（→ `sys_user.org_id`）、`user_status`（05 枚举 `ACTIVE / DISABLED`，实装 `USER_*`，对照见篇首）、`keyword`、分页参数均可空。
2. **组装查询**：目标表 `sys_user`（05 P.2），医生身份 = `role_view = 'doctor'`（承载实装 `identity_type = DOCTOR`），固定排除软删除行（05 `sys_user` 设 `deleted_at`）；`org_id / user_status` 精确匹配；`keyword` 对 `real_name / username / phone` 三字段模糊匹配（`phone` ※05 未含列）。
3. **分页查询**：按 `id` 升序，`per_page` 缺省 15。
4. **Resource 组装**：`real_name / username / org_id / user_status / last_login_at` 取自库内字段；`org` → `organization`（`org_id` 关联输出 `org_name`，不冗余存储）；`password` 不输出；`phone / email / identity_type / home_route` ※05 未含，按实装迁移输出。

---

### 4.2 POST `/api/v1/doctors` — 录入医生

**Body**

| 字段 | 必填 | 规则 |
|------|------|------|
| real_name | 是 | max:100 |
| username | 是 | unique:users |
| password | 是 | min:6 |
| org_id | 否 | exists:organizations |
| phone / email | 否 | |
| home_route | 否 | max:200 |
| user_status | 否 | USER_ACTIVE / USER_DISABLED |

服务端：`identity_type=DOCTOR`，`password` → `Hash::make` 存 `password_hash`。

#### 代码逻辑

依据：05 `sys_user` 表写入（P.2：password 仅存 bcrypt 散列，05 §5.5 敏感数据建议）。

1. **参数校验**（本节 Body 表）：`real_name`（max 100）/ `username`（`sys_user.username` 唯一）/ `password`（min 6）必填；`org_id` 引用 `organization.id`；`phone / email / home_route` ※05 未含；`user_status` 限 05 枚举（默认 `ACTIVE`）。
2. **落库** `sys_user`（05 P.2）：`password` 经 bcrypt 散列后存 `password` 列（禁止明文，05 §5.5 敏感数据建议）；写入 `real_name / username / org_id`（→ `organization.id`）、`user_status` 缺省 `ACTIVE`、`role_view = 'doctor'`（医生身份，承载实装 `identity_type = DOCTOR`）。
3. **返回 201**：`{ data: DoctorResource }`（不含 password 字段）。

---

### 4.3 GET `/api/v1/doctors/{id}` — 医生详情

路径参数为 `users.id`；非 DOCTOR 身份返回 **404**。

#### 代码逻辑

依据：05 `sys_user` 表主键查询（P.2）。

1. **主键查询**：`sys_user.id`，排除软删除行，未命中返回 404。
2. **身份校验**：`role_view <> 'doctor'`（承载实装非 DOCTOR）→ 404。
3. **返回** `{ data: DoctorResource }`（password 不输出；`org` → `organization` 关联输出）。

---

### 4.4 PUT/PATCH `/api/v1/doctors/{id}` — 更新医生

**Body**：同创建，字段均为 sometimes；若传 `password` 则重新哈希。

#### 代码逻辑

依据：05 `sys_user` 表更新（P.2）。

1. **查目标行 + 身份校验**（同 §4.3：不存在或非 doctor 均返回 404）。
2. **参数校验**：Body 同 §4.2、全部 sometimes 可选；`username` 保持唯一校验。
3. **组装更新**：仅收集传入字段——05 库内列 `real_name / username / org_id / user_status`；传入 `password` 时重新 bcrypt 散列（※05 列名 `password`）；`phone / email / home_route` ※05 未含，按实装迁移写入。
4. **落库**：UPDATE `sys_user`（`updated_at` 自动刷新），返回 200 `{ data: DoctorResource }`。

---

### 4.5 DELETE `/api/v1/doctors/{id}` — 删除医生

HTTP **204**，软删除。非 DOCTOR **404**。

#### 代码逻辑

依据：05 `sys_user` 设软删除标记列 `deleted_at`（05 §4 通用约定）。

1. **查目标行 + 身份校验**（同 §4.3：不存在或非 doctor 均返回 404）。
2. **软删除**：UPDATE `sys_user` SET `deleted_at = now()`（保留账号留痕，不物理删除；05 §4 通用约定 `sys_user` 设软删除标记列）。
3. **返回 204** No Content。

## 5. 接口清单 · 诊疗记录（Dr 页数据面板）

与 **3.4 基层远程监护** 共用 REST，Dr 页侧重「近期记录列表」展示。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/clinical-records` | 按 `doctor_user_id`、`org_id` 筛选 |
| POST | `/api/v1/clinical-records` | 基层医生录入接诊 |
| GET | `/api/v1/clinical-records/{id}` | 详情 |
| PUT/PATCH | `/api/v1/clinical-records/{id}` | 更新 |
| DELETE | `/api/v1/clinical-records/{id}` | 删除 |

**POST Body 摘要**：`patient_id`, `doctor_user_id`, `visit_at` 必填；`record_type` 默认 OUTPATIENT；`chief_complaint`, `diagnosis`, `treatment` 等可选。

详见《01-基层调度板块接口.md》§6。

#### 代码逻辑（复用说明）

诊疗记录 5 个 REST 与 01 文档 §6 完全共用，代码逻辑见《01-基层调度板块接口.md》§6.1–6.3 各「代码逻辑」小节，不在此重复。Dr 页调用要点（依据 04 §5.3.3）：

Dr 页面板并行请求（plate-three-backend-enhance.js，04 §5.3.3）：`hxBackend.list('/doctors', { per_page: 20 })` → §4.1（`sys_user`，`role_view = 'doctor'`）；`hxBackend.list('/clinical-records', { per_page: 15 })` → 01 §6.1（`clinical_record` 表）。目标表 `clinical_record`（05 P.4）：`record_code / patient_id / doctor_id / chief_complaint / diagnosis / visit_at`，`doctor_name` 由 `doctor_id → sys_user.real_name` 关联输出。GET 筛选要点：`doctor_user_id → doctor_id` 精确匹配（本页侧重点）；POST 录入：`patient_id / doctor_user_id / visit_at` 必填，`record_code` 模型生成，201 返回。
