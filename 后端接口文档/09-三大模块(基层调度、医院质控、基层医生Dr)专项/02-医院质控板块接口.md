## 4. 接口清单 · 4.2 质控统计

### 4.1 GET `/api/v1/qc-issues-report` — 质控报表聚合

| 项目 | 内容 |
|------|------|
| 前端 | `/#/medical-quality/reports` API 面板 |
| 说明 | 级别分布、状态分布、机构维度统计 |

**响应字段**

| 字段 | 类型 | 说明 |
|------|------|------|
| updatedAt | string | ISO 8601 |
| total | int | 整改单总数 |
| by_severity | object | key=severity，value=count |
| by_status | object | key=qc_status，value=count |
| by_org | array | 每项见下表 |

**by_org[]**

| 字段 | 说明 |
|------|------|
| supervise_target | 督查对象名称 |
| total | 总数 |
| closed | 已销号数 |
| overdue | 超期未关闭数 |
| on_time_rate | 已关闭中按期完成比例 0~1，nullable |

**示例**

```json
{
  "updatedAt": "2026-10-13T20:00:00+08:00",
  "total": 12,
  "by_severity": { "SEVERITY_HIGH": 2, "SEVERITY_MEDIUM": 7, "SEVERITY_LOW": 3 },
  "by_status": { "QC_OPEN": 4, "QC_RECTIFYING": 3, "QC_CLOSED": 5 },
  "by_org": [
    {
      "supervise_target": "威远县人民医院·急诊科",
      "total": 5,
      "closed": 2,
      "overdue": 1,
      "on_time_rate": 0.5
    }
  ]
}
```

#### 代码逻辑

依据：04 §5.2.4（前端报表面板拉取聚合）+ 05 `qc_issue` 表（模块 4 §4.2）；聚合派生不落库（05 §5.3）。

1. **目标表** `qc_issue`（05 模块 4 §4.2），固定排除软删除行（`deleted_at IS NULL`）。
2. **total**：整改单总数（count）。
3. **by_severity**：按 `severity` 分组计数（05 枚举 `HIGH / MEDIUM / LOW`，实装 `SEVERITY_*`）。
4. **by_status**：按 `status` 分组计数（05 枚举 `QC_OPEN / QC_CLOSED`，实装另有 `QC_RECTIFYING`，见 §7.1）。
5. **by_org**：按 `supervise_target`（机构名称快照，05 §5.2 反范式）分组——`total` = 总数；`closed` = `status = QC_CLOSED` 数；`overdue` = 未关闭且 `deadline < now` 的行数；`on_time_rate` = 已关闭中 `closed_at ≤ deadline` 的比例，无已关闭行时为 null。
6. **返回裸 JSON**：`updatedAt`（服务器时间）+ `total / by_severity / by_status / by_org`（聚合派生不落库，05 §5.3），响应形态见本节示例。

### 4.3 GET `/api/v1/qc-standards/summary` — 标准汇总（Mock 契约）

对齐 `qc-standards.json`，供 `QcStandards.vue` 与 `fetch('/api/qc-standards.json')`。

**响应**

| 字段 | 说明 |
|------|------|
| version | 当前启用标准的最新 version |
| updatedAt | 服务器时间 |
| standards[] | id, name, target, samplePeriod, complianceRate |
| recentEvents[] | at, standardId, ok, note |

**complianceRate 计算**：关联 `qc_issues` 中 `related_type=QC_STANDARD` 且 `QC_CLOSED` 的按期完成率；无样本时回退 `target_rate`。

**recentEvents**：最近 10 条 `qc_issues`，`ok` 由 `check_result=达标` 或 `is_on_time_completed=true` 推导。

#### 代码逻辑

依据：04 §5.2.1（质控标准页拉取 summary；开发期 `fetch('/api/qc-standards.json')` 经 bridge 替换为本接口）+ 05 `qc_standard_version` / `qc_standard` / `qc_check_record` 表。

1. **version**：目标表 `qc_standard_version`（05 模块 4 §4.2），取 `version_code` 最新一行。
2. **standards[]**：目标表 `qc_standard`（`version_id` 对应 ① 版本，`enabled = 1`）；输出映射（05 数据字典注释）`standard_code → id`、`name → name`、`target → target`、`compliance_rate → complianceRate`（库存百分数值）；`samplePeriod` ※05 未含。
3. **recentEvents[]**：最近 10 条抽检记录——05 落库形态目标表 `qc_check_record`（`check_at → at`、`ok → ok`、`note → note`），`standard_id` → `qc_standard.standard_code` 输出 `standardId`；实装改为 `qc_issues` 最近 10 条推导 `ok`（`check_result = 达标` 或 `is_on_time_completed`，`related_type` 等列 ※05 未含）。
4. **complianceRate 计算口径**（本文档）：`qc_issues` 中 `related_type = QC_STANDARD` 且 `QC_CLOSED` 的按期完成率，无样本回退 `target_rate`——`related_type / target_rate` ※05 未含；05 形态由 `qc_standard.compliance_rate` 承载。
5. **返回裸 JSON**：`version / updatedAt / standards / recentEvents`（对齐 `qc-standards.json`）。

**业务**：非 QC_CLOSED → QC_CLOSED；`is_on_time_completed` = `due_at` 为空或 now≤due_at；版本冲突 **409**。

#### 代码逻辑

依据：05 `qc_issue` 闭环字段（`status=QC_CLOSED / closed_at / closed_by`，05 §2.2 闭环动作写入项）；`check_result`/`state_version` 列 ※05 未含。

1. **查目标行**：`qc_issue.id`（排除软删除行），未命中返回 404。
2. **参数校验**（本节 Body）：`check_result` 必填（※05 未含，实装列）、`state_version` 必填（乐观锁 ※05 未含）。
3. **乐观锁校验**：同 §4.10，库中版本与请求不一致 → 409。
4. **状态机**：已是 `QC_CLOSED` 则幂等返回；非 `QC_CLOSED` 才销号。
5. **落库**（UPDATE `qc_issue`）：`status = QC_CLOSED`（05 枚举：已闭环）、`closed_at = now()`（闭环时间）、`closed_by` = 当前登录人（→ `sys_user.id`）；`check_result / is_on_time_completed`（= `due_at` 为空或 now ≤ `due_at`，实装列）※05 未含——05 形态下按期与否由 `closed_at ≤ deadline` 可推导（见 §4.2 导出逻辑）。
6. **返回 200**：`{ data: QcIssueResource }`。

---

### 4.12 DELETE `/api/v1/qc-issues/{id}` — 删除

HTTP **204**，软删除。

#### 代码逻辑

依据：05 `qc_issue` 设软删除标记列 `deleted_at`（05 §4 通用约定）。

1. **软删除**：UPDATE `qc_issue` SET `deleted_at = now()` WHERE `id = ?` 且未删除（05 §4 通用约定 `qc_issue` 设软删除标记列），未命中返回 404。
2. **返回 204** No Content。

### 5.2 POST `/api/v1/sla-records` — 登记时限记录

| 字段 | 必填 | 说明 |
|------|------|------|
| kind | 是 | 时限类型 |
| rule_id | 是 | 规则 ID |
| subject | 是 | 对象描述 |
| started_at | 是 | 开始时间 |
| limit_minutes | 是 | ≥1 |
| owner / role_view | 否 | |
| arrived_at | 否 | 到达后重算 used_minutes、overtime |

服务端自动计算 `used_minutes`、`overtime`（未到达则按当前时间计时）。

#### 代码逻辑

依据：05 `sla_record` 写入（`limit_minutes` 为登记时刻阈值快照，05 §5.2 反范式③）+ 05 `sla_rule`（逻辑外键 rule_code）。

1. **参数校验**（本节 Body 表）：`kind / rule_id / subject / started_at / limit_minutes`（≥1）必填，`owner / role_view / arrived_at` 可空——`kind / rule_id → rule_code`（05 注释：规则编码，逻辑关联 `sla_rule.rule_code` 弱外键）、`subject` 与 `rule_code` 组成前端去重键 `kind|subject`、`started_at` ※05 未含该列（计时起点由 `created_at` 承接，登记即计时）、`limit_minutes` 为登记时刻阈值快照（05 §5.2 反范式③）、`owner` 为「随车组/当班医生」文本（05 §6-8）。
2. **计时与超时判定**（服务端计算，不入参）：计时起点 = `started_at`；终点 = `arrived_at`，未到达按当前时间计时；`used_minutes` = 起止分钟差（向上取整）；`overtime` = `used_minutes > limit_minutes`（05 默认 0）。
3. **落库** `sla_record`（05 模块 4 §4.1）：写入 `rule_code / subject / owner / limit_minutes / used_minutes / arrived_at`（可空，未到达）/ `overtime`；`role_view` ※05 未含按实装写入。
4. **返回 201**：`{ data: SlaRecordResource }`（对外 `id = sla_code`，见 §5.3）。

### 5.3 GET/PUT/DELETE `/api/v1/sla-records/{id}`

`{id}` 为表主键；Resource 对外 `id` 字段为 `sla_code`。更新时若补录 `arrived_at` 会重算超时。

#### 代码逻辑

依据：05 `sla_record` 表单表操作（05 无软删标记列 → 物理删除）。

2. **PUT/PATCH 更新**：Body 同 §5.2、全部 sometimes 可选；补录 `arrived_at` 时重算——`used_minutes` = 计时起点（`started_at`，※05 未含则回退 `created_at`）至 `arrived_at` 分钟差；`overtime` = `used_minutes > limit_minutes`（快照阈值不变）。
